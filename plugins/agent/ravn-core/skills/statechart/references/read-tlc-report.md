# Read the TLC report

- **Marks:** `breaks` marks a state that breaks a rule; `mayBreak` means only some underlying states do. Read the legend for every rule represented by a mark. On parallel views, a region state is marked when every combination containing it can break a rule; otherwise an unmarked violating combination marks all its component states.
- **Bounds:** TLC explores past rule violations. Keep the state space finite with small constants or a constraint. `VIEW` and `SYMMETRY` collapse states: an arrow can reach the representative rather than the literal target. TLC checks rules on states reached beyond constraints without exploring or deadlock-checking those states. An `ACTION_CONSTRAINT` can exclude a step even when its target is reachable by another action. The report and chart can still include the excluded final step or state when it ends a shortest bug path.
- **Deadlock:** TLC also considers a correct terminal state a deadlock when there is no step out. Add a named `Done` action with `UNCHANGED vars` that is legal only in terminal states. If the spec already has a rule named `NoDeadlock`, the generated check is `CHECK_DEADLOCK`.
- **Coverage:** The command checks the config as written with one worker, then removes broken rules one by one and reruns to find the others. After the first failure each run is capped at 100,000 distinct states. A cap or error leaves unresolved rules under “Rules not checked,” not proved. To close that gap, make the model smaller or take the known broken rules out of a scratch config and run again. The bound changes variable ordering, so a property can produce a different counterexample from an unbounded run.
- **Artifacts:** `tlc.out` is TLC on the original config; `tlc-RULE.out` is the rerun that found the named rule when needed. Above 500 states the chart shows only paths to rule violations. When all checked rules hold at that size there is no `chart.mmd`; the report still gives the state count and coverage. Reduce the model to see the full graph.
